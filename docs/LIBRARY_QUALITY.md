# Artifact library quality audit

Audit of the detection queries in ORCA's artifact library (`ref_artifact_library`: `surgical_yaml` and `custom_vql`), for Windows targets, against what Velociraptor 0.77 actually does and against MITRE ATT&CK v19.2's detection analytics. Generated by the audit scripts; numbers are per technique unless stated.

## How it was tested

1. **Velociraptor's behaviour was measured, not assumed**: string escaping, regex engine, number/text comparison, case rules, the shape of parsed event rows (see *Rules for writing library queries* below). Every check is based on those measurements.
2. **Real event schemas**: the field names and value types of every event were read from this machine's logs (Sysmon, Security, PowerShell, System, ...) and from the Windows event provider manifests (Security-Auditing: 421 events, Sysmon: 30, ...).
3. **Static analysis of every query** (exactly what the agent runs, after its own rewrites): which log and event IDs it reads, whether those events exist in that log, whether every field exists in those events, every regex run through Velociraptor against a string it was meant to match, number/text comparisons, and Velociraptor's own `artifacts verify`.
4. **Alignment with ATT&CK**: each technique's event sources compared with the log sources and event codes of ATT&CK v19.2's Windows detection analytics for that technique.
5. **Live run**: every query part run on a Windows 10 workstation with Sysmon (Security log: last 24 h; Sysmon: 67 MB), counting rows, errors and queries that return thousands of rows on a normal machine.

Note: Windows Defender on the workstation blocks a velociraptor *command line* that contains indicator strings (`invoke-mimikatz`, `lsadump::secrets`, ...). The ORCA agent is not affected: it passes each query in a file (`query -f`).

Scope: 601 Windows techniques. 77 library queries for Linux/macOS were left out (a Windows agent can't run them).

### Artifacts that never loaded

219 of 1276 YAML artifacts / VQL queries are rejected by Velociraptor's own `artifacts verify` (mostly artifact names with a part starting with a digit, e.g. `...T1003.001`, and YAML syntax errors). ## What the automatic repair changed

565 techniques changed. Every change is one of the defects above with an unambiguous fix; each technique's list of changes is in `library_scorecard.csv` and in the migration. Individual edits, by kind (a technique usually has several):

- blank output column -> the real field (time, computer, event ID, EventData.X): 2409
- regex rewritten so Velociraptor sees the pattern the author wrote (raw '''...''' string): 1410
- event read from the log it actually occurs in: 458
- `System.EventID` -> `System.EventID.Value`: 316
- filter on an undefined name -> the real field (EventData.X, System.Channel, ...): 282
- field that doesn't exist in the event -> the event's real field: 233
- `FullPath` (removed in Velociraptor 0.7) -> `OSPath` on file/registry rows: 173
- time window relative to now() removed (see below): 147
- text compared to a number field -> number: 136
- invalid artifact name fixed (the YAML never loaded): 50
- regex on a numeric access mask -> run on its hex form: 33
- path text backslashes doubled: 5
- `ORDER BY a, b` (parse error) -> one column: 3

**Time windows**: 147 filters in 71 techniques only looked at events from the last N days *before the collection ran* (`EventTime > now() - 604800`). The name they used was undefined, so they returned nothing at all; and for a disk image examined after the fact a window relative to *now* is wrong anyway. They were removed: the query covers the whole log. Some of these techniques now return every event of their type (they show as *noisy*): they were silent before, so they still need a real content filter.

The repair is applied by a migration that only replaces a row whose text is still exactly the shipped version, so a query an analyst edited in the Artifact Library Editor is left alone.

## Hand repairs (round 2)

The techniques the automatic repair couldn't fix or had to hold back were rewritten by hand (70 techniques; `migrations/repair_library_queries_2.sql`). Each query part was checked with `artifacts verify`, run against the Atomic Red Team VM's disk (below) and against a normal workstation for noise. Held-back queries got a real filter (e.g. T1134.002: *any* lsass access, 558,000 rows on one workstation; now token-theft patterns only, 15). Six techniques Velociraptor refused to load at all (unknown functions or arguments) were rewritten too. Per-technique notes are in `library_scorecard.csv` (column `hand_repair`).

**Not observable on a host (14)**: ATT&CK lists no host data source for these; they happen on attacker infrastructure or in public sources (buying domains, scanning, researching the victim). Their library text is left as is, and the technique's analysis steps now start with *NOT OBSERVABLE ON THE HOST*, so an empty result isn't read as evidence of absence: T1583 (Acquire Infrastructure), T1583.004 (Server), T1584.002 (DNS Server), T1584.003 (Virtual Private Server), T1587 (Develop Capabilities), T1590.002 (DNS), T1590.006 (Network Security Appliances), T1591.001 (Determine Physical Locations), T1592.003 (Firmware), T1595.002 (Vulnerability Scanning), T1596.001 (DNS/Passive DNS), T1596.005 (Scan Databases), T1597.001 (Threat Intel Vendors), T1608.001 (Upload Malware).

## Attack simulation (Atomic Red Team)

Ground truth: the Windows Atomic Red Team tests were run technique by technique on an isolated Windows 11 Enterprise VM (no network during the tests; Sysmon with the sysmon-modular config, full audit policy incl. command lines, PowerShell script-block logging), logging each technique's start and end time. Windows Defender stayed on (Tamper Protection can't be switched off unattended; only the test folders were excluded), so some tests were blocked part-way, as they would be on a protected target. Tests that wreck the lab (shutdown, disk wipe, encryption, account lock-out, service stop, DoS) were skipped. The run covered 210 techniques in alphabetical order before the VM restarted itself; the remaining ones, mostly log clearing and defence evasion (deliberately ordered last so they couldn't wipe the earlier evidence), were not run.

The VM's disk before and after the attacks was mounted on the analyst workstation and each technique's queries (original, after the automatic repair, after the hand repair) were run through the ORCA agent against both, exactly the disk-image path an analyst uses. ## Rules for writing library queries (Velociraptor 0.77, verified)

- **Backslashes in strings**: in `'...'` and `"..."`, `\\` becomes one backslash, `\n \t \' \"` are escapes, and any other backslash is **dropped** (`'C:\Users'` is `C:Users`, `'\d'` is `d`). For regexes use triple quotes, which keep text as written: `=~ '''.*\\CurrentVersion\\Run'''` (regex `\\` = one literal backslash).
- **Event rows** from `parse_evtx()` have only `System`, `EventData` (or `UserData`) and `Message`. Use `System.EventID.Value` (not `System.EventID`), `System.TimeCreated.SystemTime`, `System.Computer`, `System.Channel`, `EventData.<Field>`. Bare `EventTime`, `Computer`, `CommandLine` are empty.
- **Event numbers are per log**: Sysmon 1 is in `Microsoft-Windows-Sysmon%4Operational.evtx`, not `Security.evtx`.
- **Field names** are case-sensitive and differ per event (Security 4688: `NewProcessName`, `ParentProcessName`, `CommandLine`; Sysmon 1: `Image`, `ParentImage`, `CommandLine`; Sysmon 10: `SourceImage`, `TargetImage`, `GrantedAccess`, `SourceProcessGUID`).
- **Numbers vs text**: `=` and `IN` never convert. `GrantedAccess` (2097151 = 0x1FFFFF), `LogonType`, `DestinationPort`, event IDs are numbers: `GrantedAccess IN (0x1410, 0x1010)`, not `('0x1410')`.
- `=~` is case-insensitive; `=` and `IN` are case-sensitive. Regex engine is Go RE2: no lookahead/lookbehind.
- A SELECT alias can be used in WHERE; the original name after renaming can't.
- `ORDER BY` takes one column. Artifact names: dot-separated parts that don't start with a digit.
- Check a new query with `velociraptor artifacts verify <file.yaml>` (one file at a time).
